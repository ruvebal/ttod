## 0. What this phase actually is

TTOD (`AGENTS.md`) is a governed, CLI-only, human-curated wisdom database: `ttod.yml` (v3.1.0
schema), written only through `ttod_core/repository.py` atomic transactions via `cli.py`. It has
no web surface. R1 builds that web surface's read path and its one permitted write path: a thin
FastAPI façade that imports `ttod_core` **in-process** (not via subprocess/CLI shell-out — this
was a genuine either/or in earlier drafts of the master document and is now resolved: `backend` is
Python, `ttod_core` is a plain importable package with no CLI-only side effects in its library
functions, and shelling out would add process-spawn latency and a second failure mode for no
benefit). `cli.py` remains the tool for humans/scripts at a terminal; `backend` is a second,
independent consumer of the same `ttod_core` library, not a wrapper around the first consumer.

R1 does **not** reimplement a "plugin registry" or invent a generic architecture — every endpoint
below calls a `ttod_core` function that already exists and that `cli.py` itself already calls.

**Runtime transport frozen after implementation review (2026-09-05):** R2 serves FastMCP
Streamable HTTP at `${MCP_SERVER_URL%/}/mcp`. R1 uses `fastmcp.Client` to call R2's
`semantic_retrieval(query, top_k, contextTag, section)` tool and validates the
`{results, indexDigest, indexedQuotes}` envelope. Retrieval failures fail closed; production must
not silently fall back to a duplicate in-process retriever.

This is one of three instructor-owned lanes (with R2 — FastMCP server, and R3a — walking-skeleton
scaffold) that must all be green before the **cohort-start gate** opens and 7 students begin R3b–R7.
R1, R2, and R3a are mutually independent at the dependency-graph level (all three depend only on
R0, not on each other) — but they converge physically: R3a's `docker-compose.yml` builds and wires
`services/backend` (this phase) and `services/mcp` (R2). Since the same person owns all three,
sequence them practically (e.g. get R1's and R2's Dockerfiles buildable before R3a's compose
bring-up step is meaningful) but do not treat this as a hard dependency edge — it is a
coordination note, not a gate.

## 3. Non-negotiable boundaries (restated in full — do not rely on having read the master document)

### 3.1 Inherited from TTOD Phase Q — unconditional, no exceptions

- **`ttod.yml` has exactly one write path**: `ttod_core/repository.py` atomic transactions (the
  same transactions `cli.py`'s `add`, `proposal accept`, `deprecate`, `erase`, `migrate apply`
  invoke). `backend` is **read-only** against canonical data. It may call
  `ttod_core.proposals.ProposalStore`/`create_proposal` to *stage* a proposal (the `oracle/propose`
  endpoint, §4.5); it may **never** call anything that allocates a canonical ID or accepts a
  proposal (`TTODRepository.accept_proposal`, `add`, `deprecate`, `erase`, `migrate apply` are all
  off-limits to every request handler, unconditionally).
- **No silent provenance promotion.** Anything the Oracle (LLM) surfaces as a candidate new
  aphorism is `origin: blackbox` by construction and requires human `validated_by`/`reviewer_id`
  before it can ever become an active quote.
- **Rights gate public export.** Only `status: active` quotes with a resolved, public-permitted
  `rights` block may ever be serialized to a public endpoint. Unresolved or restricted content is
  filtered **server-side** (in `backend`), never merely hidden client-side.
- **Local-only AI.** All LLM calls go through an Ollama-compatible adapter. No OpenAI/Anthropic/
  cloud LLM SDK or API call anywhere in `services/backend`.
- **Content stays CC BY-NC-SA 4.0.** Attribute per `LICENSE-CONTENT`; code stays MIT.
- **Counts are never hardcoded.** Any quote/section/tag count exposed by an endpoint is computed
  from a live snapshot, never baked into backend code or fixtures.

### 3.2 Inherited from the stack draft, reconciled with studio infra

- **No heavy external DB.** `backend`'s storage adapter *is* `ttod_core` reading `ttod.yml`. No
  PostgreSQL/pgvector, no second database to design. The corpus (229 records today, hundreds at
  most) fits entirely in memory; parsing costs milliseconds. Cache the computed projection
  (wisdom-sample, graph) in-process, keyed on `ttod.yml`'s mtime/digest, invalidate and recompute
  when either changes. This serves any number of concurrent readers the way a static site scales,
  without a DB and without a second source of truth that could drift from `ttod.yml`.
- **No heavy native dependencies** — the stack must run on an 8 GB RAM student laptop.
- **No unbound host ports** (`80`, `443`, `11434`) in the base `docker-compose.yml` (R3a owns that
  file, but `backend`'s own service block must not declare one either); use `.env`/override files.
- **Ollama is three-tier, not one switch.** `backend` never hardcodes a model tag or a single
  placement — both come from `.env`: `OLLAMA_MODE` (`host`|`container`), `OLLAMA_MODEL`,
  `OLLAMA_BASE_URL`. Individual dev: bare-metal, `qwen3.8:27b`-class (confirmed pulled locally,
  2026-09-06 `ollama list`: 27.3B params, `Q4_K_M`, 262144 context — no substitution needed).
  Lilith/Scaleway: containerized, light model (`llama3.2:1b`/`qwen2.5:1.5b`) — **neither tag is
  confirmed pulled anywhere as of this runbook's generation** (re-verified at R0 time: `ollama
  list` shows `qwen3.8:27b`, the `qwen2.5:{3b,7b,32b-instruct,72b-instruct-q4_K_M}` family,
  `nomic-embed-text`, `llama3.2-vision` — a *different* model from the required `llama3.2:1b` — and
  the `thessia-*` fine-tunes, but no `llama3.2:1b` and no `qwen2.5:1.5b`). R1 itself does not pull
  models (that is R2's/R3a's compose bring-up step), but do not write `backend` code that assumes
  a light-tier model is already present in dev — always resolve the model tag from `OLLAMA_MODEL`
  and fail with a clear error (not a silent fallback) if the configured tag 404s against Ollama's
  `/api/tags`.

## 4. Domain contract this phase authors (`services/frontend/src/types/domain.ts`)

R1 does not own `services/frontend`, but it is the **source of truth** the frontend's
`domain.ts` must match — every field below comes from a real `ttod_core`/`schema/` shape, not an
invented one. Restated in full so this runbook does not depend on any other file being open:

```typescript
// Wire projection of the TTOD v3 quote record (schema/quote.schema.json), rights-filtered.
// Internal-only fields (validation.reviewer_id, source_refs, ancestry) are never sent to the client.
export interface WisdomEntry {
	id: string;
	section: string;
	subsection?: string;
	level: 'beginner' | 'intermediate' | 'advanced' | 'master';
	text: string;
	teaches: string;
	tags: string[];
	related: string[];
	origin: 'human' | 'studio' | 'blackbox' | 'mixed' | 'legacy-unknown';
	// ISO 639-1 (e.g. "en", "es"). Every quote is single-language; a translation is a separate
	// record linked via a "translation_of" edge (see GraphLink below), not a locale-keyed field on
	// this one. Confirmed populated on every live record as of R0 generation (229/229 carry "en").
	lang: string;
	rights: {
		license: string; // e.g. "CC-BY-NC-SA-4.0" — hyphenated, the real schema/data value, not the
		// display-formatted "CC BY-NC-SA 4.0" prose used in docs. A contract test asserting this
		// field must use the real string.
		holder?: string;
	};
}

// Matches ttod_core/exporter.py Exporter._graph_nodes() exactly — confirmed by reading the code
// 2026-09-06: {id, section, origin, status, text, lang}. No invented "label"/"group".
export interface GraphNode {
	id: string;
	section: string;
	origin: WisdomEntry['origin'];
	status: 'active' | 'deprecated' | 'erased';
	text: string;
	lang: string;
}

// Matches Exporter._graph_edges(): "rel" is a real relation type, not a fabricated numeric weight.
export interface GraphLink {
	source: string;
	target: string;
	rel: 'related' | 'immediate_parent' | 'root_source' | 'deprecated_by' | 'superseded_by' | 'translation_of';
}

// Request payload for POST /api/v1/oracle/stream.
export interface OracleQueryPayload {
	query: string;
	contextTag?: string; // synced from the graph island's selected node
	sessionHistory: string[];
}

// SSE response envelope for /api/v1/oracle/stream. "mode" is the grounded/creative marker (§5.2
// below) — the terminal must render these two distinguishably; a creative answer is never shown
// as if it cites a real quote.
export interface OracleResponseChunk {
	mode: 'grounded' | 'creative';
	citedQuoteIds?: string[]; // present only when mode === 'grounded'
	text: string; // streamed token/segment
}

// Body for POST /api/v1/oracle/propose (§4.5) — human-initiated only, never automatic. Writes a
// proposal (origin: blackbox), never a canonical quote.
export interface OracleProposeRequest {
	query: string;
	creativeAnswer: string;
	suggestedSection?: string; // pre-filled from below-threshold nearest neighbors
	suggestedTags?: string[]; // "the tags around" — a starting point, not a final answer
}
```

### 4.1 How the graph is derived from `ttod.yml` (read this before implementing `GET /api/v1/graph`)

There is no separate graph store. The graph is a **computed projection** of the same flat quote
list, regenerated on every export:

1. **Nodes = quotes, trimmed.** Every record under `ttod.yml`'s `quotes:` list becomes exactly one
   `GraphNode` via `Exporter._graph_nodes()` — `id, section, origin, status, text, lang`. No layout
   information (x/y, size) lives in the data; that is a frontend (R4) concern.
2. **Edges = relational fields, flattened**, via `Exporter._graph_edges()`:

   | Field on the quote                                            | Emitted edge `rel` |
   | --------------------------------------------------------------| ------------------- |
   | `related: [id, ...]`                                          | `related`           |
   | `relation_edges: [{target, relation_type}]`                   | `<relation_type>`   |
   | `relation_edges: [{target, relation_type: "translation_of"}]` | `translation_of`    |
   | `immediate_parent_refs: [id]`                                 | `immediate_parent`  |
   | `root_source_refs: [id]`                                      | `root_source`       |
   | `deprecated_by`                                                | `deprecated_by`     |
   | `superseded_by`                                                | `superseded_by`     |

3. **Nothing is persisted separately.** `GET /api/v1/graph` calls the same
   `export_graph`/`_graph_nodes`/`_graph_edges` code `cli.py graph` already calls, through R1's
   own in-memory cache keyed on `ttod.yml`'s mtime/hash — never a materialized graph table.

## 5. Endpoints to build (this is R1's actual scope)

Uvicorn on `8000`, mounted under `/api/v1/*` behind R3a's Caddy reverse proxy.

1. **`GET /health`** — process liveness + a real `ttod_core` import/call check (e.g. confirm
   `TTODRepository` can be constructed), not just "process is up."
2. **`GET /api/v1/schema/definitions`** — serves the real files under `schema/`
   (`quote.schema.json`, `ttod.schema.json`, `proposal.schema.json`) as-is. This *is* the contract
   source of truth for `domain.ts`, not an invented export.
3. **`GET /api/v1/wisdom/sample`** — calls `TTODRepository`/`Exporter` directly and returns a
   rights-filtered, `status: active` projection (§3.1's rights-gate rule, enforced here).
4. **`GET /api/v1/graph`** — calls `Exporter.export_graph()` directly (§4.1). Two clean calls for
   the same snapshot must be byte-identical (same guarantee `cli.py graph` already gives).
5. **`POST /api/v1/oracle/stream`** — see §5.1–§5.3 below.
6. **`POST /api/v1/oracle/propose`** — see §5.4 below.

### 5.1 Language matching (not translation)

Detect the input message's language server-side (a lightweight detector, or the light model's own
instruction-following: "respond in the language the user wrote in"). If it is `en` or `es`, respond
in that language; any other detected language falls back to English. This is ephemeral
request/response behavior — no persistence, no proposal, no promotion — so it carries none of
Phase S §S4′'s governance weight and needs no human-accept step. Do not conflate this with S4′:
this endpoint never writes a quote or a translation to any store.

### 5.2 Creative-mode fallback (grounded vs. creative)

**1. Retrieval confidence, not just retrieval.** `mcp-server` (R2) embeds every `status: active`
quote (derive the count from `cli.py stats` live, never hardcode it) with `nomic-embed-text`,
embeds the incoming query the same way, returns both the top-k retrieved quotes **and** their
cosine similarity scores.

**2. Below-threshold queries switch the system prompt, not the pipeline.** `oracle/stream` compares
the top score against a threshold — **start at cosine ≈ 0.55–0.6 and calibrate empirically against
real queries; this is a starting point to tune, not an asserted-correct number.** R7's runbook
owns the calibration fixture (`tests/fixtures/r_oracle_threshold_calibration.json`) — R1 must wire
the threshold as a named, easily-changed constant (not buried inline) so that fixture can actually
drive a real assertion. Below threshold, the system prompt changes from "answer using only the
retrieved context, cite quote IDs" to: *"No strong match was found in the wisdom database for this
query. Answer thoughtfully from general knowledge, but state plainly that this is not sourced from
an existing TTOD quote."* The response carries `mode: 'grounded' | 'creative'` (§4 above).

**3. Crystallizing a creative-mode answer into a proposal is explicit and human-initiated — never
automatic.** See §5.4.

### 5.3 Known, currently-live blocker inherited from Phase S — say this plainly, do not paper over it

### 5.4 `POST /api/v1/oracle/propose`

Takes a prior creative-mode exchange and an explicit human confirmation (a `/propose` chat command
or UI affordance is R5's job to build the trigger for; R1 only implements the endpoint). Never
automatic. On call:

- calls `ttod_core.proposals.ProposalStore`/`create_proposal` to write a `status: proposed`,
  `origin: blackbox` proposal — **never a canonical quote**;
- **must set `lang` on the candidate content, explicitly, not optionally.** Confirmed against live
  code: `schema/proposal.schema.json`'s `candidate_content.required` list is
  `text, section, level, origin` — it does **not** require `lang` at the schema level. But
  `TTODRepository`'s accept-transaction validation *does* require `lang` on the candidate (the same
  required-fields check Phase S's S1′ added). A proposal drafted without `lang` will save cleanly,
  pass `proposal.schema.json`, and then fail at `proposal accept` time with a confusing late error.
  `oracle/propose` sets `lang` to whichever language the creative-mode response was actually
  generated in (§5.1 already determined this per-request) — this is not optional, do not copy the
  schema's own permissiveness here;
- pre-fills `section`/`tags` from the below-threshold nearest neighbors the similarity search still
  returned;
- records `source_refs` noting the triggering query, session timestamp, and that this was
  generated in creative mode.

No code path in `oracle/propose` may allocate a canonical ID or set `status: active` — write a
negative test proving this (mirrors §S4′'s naming convention):
`tests/fixtures/r_negative_oracle_propose_no_active.json` plus an assertion that `oracle/propose`'s
output cannot reach `active` status without a separate accept call.

## 7. Rollback and mutation law (restated in full)

- The web layer is read-only against `ttod.yml` under all circumstances; a failing backend deploy
  never blocks or risks the CLI/data layer, because it cannot touch it.
- A staged proposal from the Oracle is inert until a human runs `proposal review`/`proposal accept`
  exactly as Phase Q defines; R1 introduces no new acceptance path.
- Container/image failures never touch host files outside `services/*/`, `caddy/`, and the compose
  files; nothing in R1 writes to `~/.ollama`, `ttod.yml`, `schema/`, or `exports/` except read
  access to `schema/`/`ttod.yml`.
