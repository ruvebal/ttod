## 0. What this phase actually is

This is the literal Alistair Cockburn "walking skeleton": the thinnest possible slice of the whole
Oracle Platform, working end-to-end, before anyone builds a feature on top of it. Not a full Astro
site — a minimal Astro project with Compose/Caddy wiring for **four host-mode services or all 5
containers under the explicit container profile**
(`reverse-proxy`, `frontend`, `backend`, `mcp-server`, `ollama`), a hello-world welcome route in
both `en` and `es`, and **one** live page that fetches and renders a single real quote through the
full pipeline: `Astro → backend → ttod_core → ttod.yml → back to the browser`.

R3a is one of three instructor-owned lanes (with R1 — FastAPI backend, R2 — FastMCP server) that
must all be green before the cohort-start gate opens and 7 students begin R3b–R7. R3a is the one
that physically assembles the other two: its `docker-compose.yml` builds and wires
`services/backend` (R1) and `services/mcp` (R2). R3a does not need to wait for R1/R2 to be fully
*feature*-complete (§5's oracle-stream/oracle-propose endpoints, R2's full retrieval pipeline) — it
only needs R1's `/health` and one real read endpoint (`/api/v1/wisdom/sample` or `/api/v1/graph`)
working, and R2's container to build and start cleanly, to prove the walking skeleton actually
walks. Full R1/R2 feature completeness and R3a's own scaffold can therefore proceed in parallel by
the same owner; the **cohort-start gate** itself does require all three phases' own reports to say
`DONE`, not just R3a's slice.

**Once this phase is green, `/api/v1/*` and `domain.ts` are frozen by construction** — R3b, R4, R5
build against that contract as independent PRs, the same "frozen interface, parallel lane"
discipline as Phase Q's Q2 lanes.

## 2. Non-negotiable boundaries (restated in full)

### 2.1 Inherited from TTOD Phase Q — unconditional, no exceptions

- **`ttod.yml` has exactly one write path** — R3a's scaffold introduces no new write surface; the
  `frontend` container is a pure consumer of `backend`'s read-only API.
- **Local-only AI.** `ollama` runs as a container (Lilith/Scaleway profiles) or is omitted entirely
  in favor of a bare-metal host instance (individual dev profile, §2.2 below) — never a cloud LLM.
- **Content stays CC BY-NC-SA 4.0** — R3a's hello-world/single-quote page must attribute per
  `LICENSE-CONTENT` even at this minimal scale, so the pattern is established before R3b builds on
  top of it, not retrofitted later.
- **Counts are never hardcoded.** Even the walking skeleton's single displayed quote is fetched
  live from `backend`, never a static fixture baked into the Astro build.

### 2.2 Inherited from the stack draft, reconciled with studio infra

- **No heavy external DB.** R3a's compose file has exactly 5 services, no database service.
- **No heavy native dependencies** — the whole stack must run on an 8 GB RAM student laptop; this
  is the phase that actually proves that budget, since it is the first time all 5 containers run
  together.
- **No unbound host ports** (`80`, `443`, `11434`) in the **base** `docker-compose.yml` — use
  `.env`/override files. Local dev/Lilith Caddy profile binds `8080`/`8443` with no TLS-issuance
  attempt (Let's Encrypt applies only to the public Scaleway `stg` deployment, R6's concern, gated
  on §0.1.3's deploy decision — not R3a's problem). **Open question this runbook does not resolve
  for you, flagged rather than guessed:** the master document explicitly says to "confirm which
  before generating R6's runbook" whether local/Lilith Caddy should use a bare no-TLS `8080/8443`
  profile or the studio's existing mkcert `*.crea-comm.loc` certificate pattern — **this is R3a's
  decision to make in practice** (R3a is the phase that writes the actual Caddy config), and this
  runbook does not pick one for you. Default to the simpler bare `8080/8443` no-TLS profile unless
  you have a specific reason to sit behind `*.crea-comm.loc` (e.g. this stack is meant to be
  reachable at a studio-consistent hostname on Lilith) — record whichever you choose, and why, in
  `PHASE-R3a-REPORT.md` so R6 does not have to re-derive it.
- **Ollama is three-tier, not one switch.** R3a's compose file must support both profiles without
  code duplication: `OLLAMA_MODE=host` (individual dev — `ollama` service **omitted entirely** from
  the running set, `backend`/`mcp-server` point at the host's bare-metal Ollama via
  `OLLAMA_BASE_URL=http://host.docker.internal:11434` or the Linux-compatible equivalent) vs.
  `OLLAMA_MODE=container` (Lilith/Scaleway — `ollama` service included, host-mapped
  `11435:11434`, named volume `ttod_ollama_data:/root/.ollama`). Use Compose profiles or an
  override file, not a hand-maintained second compose file that can drift.
  **Light-tier model pull is R3a's explicit job when `OLLAMA_MODE=container`:** re-verified at R0
  generation time, neither `llama3.2:1b` nor `qwen2.5:1.5b` is confirmed pulled anywhere. R3a's
  compose bring-up for the container profile must include an explicit `ollama pull llama3.2:1b` (or
  `qwen2.5:1.5b` — pick one as the actual default and document the choice in the report; pull the
  other only if a fallback is genuinely needed) step, e.g. as a compose `entrypoint`/init step or a
  documented manual command in the onboarding doc — do not treat "the tag is named in this document"
  as equivalent to "the tag is available."

### 2.3 Cross-platform constraints (this phase is where these actually get tested)

- Root `.gitattributes`: `* text=auto eol=lf` — add this on the same commit as the scaffold if it
  does not already exist; prevents CRLF breaking Linux-container shebangs/scripts.
- Root `.env`: `COMPOSE_PROJECT_NAME=ttod_oracle` — namespaces containers/networks/volumes so this
  stack never collides with `deviac`/`arkadia` compose projects also running on the same machine.
- Podman/Podman Compose (Docker-CLI compatible) is the reference orchestrator; plain Docker Compose
  must also work unmodified — verify both if practical, at minimum document which was actually
  tested.
- **This phase's exit gate requires reference-runtime proof**: a clean build and live browser/API
  smoke pass on one declared runtime, plus successful Compose configuration for both profiles.
  Linux/Podman and Windows/WSL2 remain R6/R7 onboarding/CI verification targets; report them as
  untested until proven instead of blocking on unavailable physical hosts.

### 2.4 Environment files and secrets discipline (student-safe by design, not by warning label)

**R3a is the phase that actually creates `.env`/`.env.example` — this section is not optional
background reading, it is literal scope for this phase.**

- **`.env.example` is committed and safe (placeholder values only); `.env` is gitignored and never
  committed.** R3a's scaffold must add `.env` to root `.gitignore` on **the same commit** that
  introduces `.env.example` — not as a follow-up. (Confirmed at R0 generation time: root
  `.gitignore` already contains an `.env*` pattern, so this rule is likely already satisfied —
  verify it still covers `.env` exactly and has not been narrowed, rather than assuming.)
- **The local walking-skeleton stack needs zero real secrets, and the onboarding doc this phase
  writes must say so explicitly.** `OLLAMA_MODE`, `OLLAMA_MODEL`, `OLLAMA_EMBED_MODEL`,
  `COMPOSE_PROJECT_NAME` are configuration, not credentials — Ollama's local API has no auth token
  to leak. If a student ever finds themselves about to type something that looks like a real secret
  (an API key, a password, an SSH private key) into this stack's `.env` for local dev, that is a
  signal something has gone off-script — the onboarding doc must say: stop and ask, don't guess a
  value in.
- **University/shared lab computers are a different threat model, not just "another laptop" — say
  this explicitly in the onboarding doc, don't assume it's obvious.** A shared machine can persist
  files, shell history, and cached tool logins across users who are not you:
  - Since local dev needs no real secrets (above), there is nothing sensitive in this stack's own
    `.env` to leak on a shared machine. The actual risk is *other* credentials — a `git`/`gh`/cloud
    CLI login left cached on a machine you don't own.
  - If a student ever authenticates any CLI tool on a shared machine, log out at the end of the
    session (`gh auth logout`, cloud provider CLI logout) rather than leaving it cached.
  - Prefer repo-local `git config` (no `--global`) on a machine you don't own.
  - Never pass a secret as a bare CLI argument — it lands in shell history and process listings
    visible to other users on a shared machine. Always via a file (`.env`), never inline, and this
    stack should never need you to anyway (previous bullet).
- **Lilith (LAN shared dev) needs no student-held credential.** It's a shared `docker-compose`
  stack reachable on the trusted studio LAN — students connect to it, they do not deploy to it with
  their own secrets. R3a's onboarding doc should mention this distinction so a student doesn't
  wonder whether they need Lilith access credentials for local dev (they don't).
- **Scaleway `stg` secrets are instructor-only, out of scope for R3a entirely** — this phase's
  onboarding doc must not ask a student to hold, type, or even see a production deploy credential.

## 3. Domain contract slice R3a scaffolds against

R3a's own live-quote page needs only the read half of the contract — it renders one `WisdomEntry`:

```typescript
export interface WisdomEntry {
	id: string;
	section: string;
	subsection?: string;
	level: 'beginner' | 'intermediate' | 'advanced' | 'master';
	text: string;
	teaches: string;
	tags: string[];
	related: string[];
	origin: 'human' | 'studio' | 'blackbox' | 'mixed' | 'legacy-unknown';
	lang: string; // ISO 639-1; every live record carries this as of Phase S's S2′ (confirmed 229/229 "en")
	rights: {
		license: string; // e.g. "CC-BY-NC-SA-4.0" — the real schema/data value, hyphenated
		holder?: string;
	};
}
```

If `services/frontend/src/types/domain.ts` does not yet exist when R3a starts (R1/R2 may not have
created it yet, depending on build order), R3a creates it with at least this interface; R1 is its
long-term source of truth and will extend it with the oracle-related types.

## 6. Rollback and mutation law (restated in full)

- The web layer is read-only against `ttod.yml` under all circumstances — R3a's compose file gives
  `frontend`/`backend`/`mcp-server` no volume mount or write path to the repository root beyond
  `backend`'s read-only import of `ttod_core`.
- Container/image failures never touch host files outside `services/*/`, `caddy/`, and the compose
  files; nothing in R3a writes to `~/.ollama`, `ttod.yml`, `schema/`, or `exports/` except the
  Ollama named volume (containerized profile only) and read access to `schema/`/`ttod.yml` through
  `backend`.

## 8. Post-phase cold review (mandatory — not a formality)

**Two propagation obligations if the cold review finds something:**

2. **If the finding is structural — it reveals the master document itself asserted something

   `PHASE-R-TTOD-ORACLE-PLATFORM-CASCADE-PROMPT.md` itself, not only this runbook, and re-check

Record findings in `PHASE-R3a-REPORT.md` under a `## Lessons for the next phase` heading — **every
student lane (R3b, R4, R5, R7) reads this report before starting**, since R3a is the foundation
they all inherit; if R3a's cold review finds the compose wiring or the Caddy TLS-profile choice
needs to change, that change must land before the cohort-start gate opens, not after students have
already started building on the wrong assumption.

## 9. Phase report status enum (restated — use exactly one)

- **DONE** — every gate in §5 passed, including the cohort-start gate itself; cold review (§8) ran
  and its findings are recorded and resolved or explicitly deferred; the report shows the actual
  `docker-compose up` output and a description (or screenshot reference) of the rendered page, not
  "should work."
- **PARTIAL** — some containers/routes shipped and are individually gate-clean, others are not;
  name exactly which — **a PARTIAL R3a does not open the cohort-start gate.**
- **BLOCKED** — cannot proceed because of an external dependency that isn't R3a's own work to fix
  (most likely: R1 or R2's Dockerfile not yet buildable, or the light-tier Ollama model tag not
  pullable in the build environment).
- **IN_PROGRESS** — a long-running step (e.g. a first-time full `ollama pull` of a multi-GB model
  on a slow connection) is genuinely still executing when the session ends.
