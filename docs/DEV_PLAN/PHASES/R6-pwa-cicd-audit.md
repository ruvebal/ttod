## 0. What this phase actually is, and the gate you must verify before starting

R6 is where the assembled platform (R3b's content, R4's graph, R5's oracle terminal, all sitting on
R1/R2/R3a's foundation) becomes an installable, offline-capable Progressive Web App with a real
CI/CD pipeline. Unlike every other student lane, **R6 must wait for R3b, R4, and R5 to all be
`DONE` — not just started, and not `PARTIAL`.** Packaging a service-worker cache list around a
half-finished graph island or an incomplete content set produces a PWA that lies about what it can
serve offline.

**Do not start this phase until you have personally confirmed** `docs/DEV_PLAN/PHASE-R3b-REPORT.md`,
`PHASE-R4-REPORT.md`, and `PHASE-R5-REPORT.md` all say `DONE`. Read each report's "Lessons for the
next phase" section in full — three separate lanes' worth of findings may affect what you build.

**R6's own scope is real engineering beyond FE II Deliverable 1's literal graded text — say this
explicitly, don't quietly absorb it into "R6 is just CI/CD."** Deliverable 1 names Astro, content
collections, i18n, islands, multi-framework integration, a Vitest+RTL+Playwright suite, and CI/CD.
It does not name PWA offline support or a Scaleway deployment. R6's PWA/CI/Scaleway work is this
document's own architecture, an extension of Deliverable 1's named "CI/CD" requirement, not an
unrelated addition — but it is genuinely more scope than the graded minimum, worth knowing as you
scope your own time.

## 2. Non-negotiable boundaries (restated in full)

### 2.1 Inherited from TTOD Phase Q — unconditional, no exceptions

- **`ttod.yml` has exactly one write path.** Nothing about PWA offline caching or CI/CD introduces
  a new write surface — the service worker caches **responses**, it never mutates canonical data,
  and CI never runs a step that touches `ttod.yml` directly.
- **Content stays CC BY-NC-SA 4.0.** The deployed `stg` site must attribute per `LICENSE-CONTENT`;
  no commercial use may be surfaced on the public deployment.
- **Local-only AI, even on the public deployment.** Scaleway `stg`'s Ollama is **containerized,
  running locally to that instance** — this is not a violation of "no cloud AI." **Clarification,
  since this is easy to misread:** "no cloud AI" means no vendor-hosted inference API (OpenAI,
  Anthropic, etc.), not "no inference on a rented server." A containerized Ollama on Scaleway is
  fine; a call to a cloud LLM vendor's API from anywhere in this stack is never fine.

### 2.2 Inherited from the stack draft, reconciled with studio infra

- **No heavy external DB** — R6 does not introduce one; the offline cache is IndexedDB (client-
  side, per-user) plus the service worker's own cache storage, not a server-side database.
- **No heavy native dependencies.**
- **No unbound host ports.** Production TLS ports (`80`/`443`) are a Caddy **production-profile**
  concern specific to the public Scaleway `stg` hostname — this is the one place in the whole
  platform where binding `80`/`443` is correct, because it is a real public hostname Let's Encrypt
  can issue a certificate for. **This must not be applied to Lilith or Tanit** — the local/Lilith
  profile (R3a's decision) stays on its non-TLS-issuance port pair.
- **Ollama is three-tier, not one switch.** Scaleway `stg` runs the same light containerized model
  Lilith does (§0.1.2) — same tag, same "verify it's actually pulled, don't assume" discipline R2/
  R3a already established. R6's deploy workflow must include an explicit pull step for whichever
  light-tier tag R3a's report recorded as the chosen default, not assume the image already has it
  baked in unless you deliberately build that into the Ollama image yourself and say so.

### 2.3 Cross-platform constraints

- CI runs on GitHub Actions' own runners (typically Linux) — cross-platform correctness for
  student laptops is R3a's/R7's concern; R6's CI job itself only needs to be correct for the CI
  runner's OS, but should not assume anything CI-runner-specific leaks into the deployed image.
- R3a verified macOS Docker as the initial reference runtime. R6 adds a Linux Docker Compose
  configuration/build smoke in CI and preserves the explicit four-service host / five-service
  container-profile distinction. Windows/WSL2 remains a documented manual onboarding check unless
  a suitable runner is deliberately added; never claim it from Linux CI evidence.

### 2.4 Environment files and secrets discipline — read this before touching CI config at all

**This is the one phase in the whole platform where real secrets genuinely exist, and they are
instructor-only by design, never distributed to students.**

- **Scaleway `stg` secrets are instructor-only, never distributed.** The SSH deploy key and
  Scaleway API token live only in the GitHub repository's Actions secrets, configured by Rubén.
  **R6's runbook — and R6's actual workflow file — must not ask a student to hold, type, or even
  see a production deploy credential at any point.** The cohort's own local `.env` files never need
  one; nothing in R6's own local-dev testing should require the student to have Scaleway
  credentials at all — build/test steps run without them, only the deploy step (instructor-gated,
  §2.5) needs them, and that step runs in CI under instructor-configured secrets, never on a
  student's machine.
- **Never pass a secret as a bare CLI argument or log line** in the workflow file — always through
  GitHub Actions' own secrets mechanism (`${{ secrets.SCALEWAY_API_TOKEN }}` etc.), never inline,
  never echoed to a log step.
- **The local walking-skeleton stack (which R6 still builds/tests against locally before touching
  CI) needs zero real secrets** — same as every other phase. If an R6 task ever seems to need a
  real credential for **local** dev/testing, that's a signal something has gone off-script — stop
  and ask.

### 2.5 Deploy gate — do not deploy before this decision record exists

**Public deployment target is Scaleway, single staging environment only (`stg.` subdomain), no
separate production, no blue/green swap** — this decision is already recorded as frozen in the
master document (§0.1.3). But **the deploy *step itself* only runs once a decision record for it
exists** at `docs/DEV_PLAN/DECISIONS/` (mirroring
[`DECISIONS/Q0-2026-08-18-RIGHTS-LICENSE-NC.md`](../DECISIONS/Q0-2026-08-18-RIGHTS-LICENSE-NC.md)'s
pattern) — **check for this file before enabling the deploy job; if it does not exist, CI builds
and tests unconditionally, but the deploy step stays disabled, full stop, no "just for CI testing"
exception.** If R6's own runbook execution needs to make this decision for the first time (rather
than finding it already recorded), that decision belongs to the product owner (Rubén), not to
whichever student is executing this runbook — flag it and wait, do not sign your own deploy
decision record.

## 3. Domain contract slice R6 works against

```typescript
// src/lib/db.ts IndexedDB record — the same shape R5 already introduced for its offline oracle
// queue. R6 extends this sync mechanism to the PWA layer generally (asset caching, not just
// oracle queries) rather than inventing a second, parallel offline-storage mechanism.
export interface OfflineLogEntry {
	id: string;
	timestamp: string; // ISO-8601
	kind: 'oracle-query' | 'error-report';
	payload: OracleQueryPayload | { errorLog: string };
	synced: boolean;
}
```

R6 does not introduce new `domain.ts` types — it wires the PWA/service-worker layer around the
contract R1/R5 already established.

## 4. Scope — what R6 builds

1. **`public/sw.js`** — custom service worker (not a generated/black-box one from a framework
   plugin, unless the team deliberately chooses one and documents the choice): **Cache-First for
   static assets, Network-First for `/api/*`.** Served with `Cache-Control: max-age=0, no-cache` so
   updates propagate promptly (R3a's Caddy config already has a route rule for this — confirm it,
   don't duplicate it in `sw.js` itself).
2. **`src/lib/db.ts` sync** — extends R5's `OfflineLogEntry` mechanism so queued offline actions
   (oracle queries, error reports) flush on reconnect at the PWA/service-worker level, not only
   when the React island happens to be mounted.
3. **PWA manifest** — installability metadata (name, icons, theme color, display mode).
4. **`.github/workflows/deploy.yml`** — Scaleway `stg` deploy, gated per §2.5. Build/test steps run
   unconditionally on every PR; the deploy step is conditional on the target branch (e.g. `main`)
   **and** the decision record's existence.
5. **`.github/workflows/test.yml`** (or a combined workflow) — CI budget: **PR feedback stays under
   5 minutes wall-clock** (unit 5's own constraint, reused verbatim) — cheap lint/typecheck gate
   first, unit/component tests next, Playwright E2E sharded across parallel jobs last, `chromium`
   project only unless a cross-browser bug is filed. (R7 owns the test suite's actual content; R6
   owns the CI orchestration around it — coordinate, don't duplicate workflow files.)
6. **Lighthouse performance budget** — a CI check (or a documented manual audit, if CI-integrated
   Lighthouse proves impractical in the time available — say which you did and why) against a
   defined budget for the assembled site.

## 6. Rollback and mutation law (restated in full)

- If R6's CI/CD step runs before the §2.5 deploy decision is signed, that is a **gate failure, not
  a warning** — block the merge, do not deploy anyway "just for CI testing."
- Container/image failures never touch host files outside `services/*/`, `caddy/`, and the compose
  files; nothing in R6 writes to `~/.ollama`, `ttod.yml`, `schema/`, or `exports/`.
- The web layer stays read-only against `ttod.yml` on the deployed `stg` environment exactly as it
  is locally — R6 introduces no new write path by virtue of being "in production."

## 9. Phase report status enum (restated — use exactly one)

- **DONE** — every gate in §5 passed; cold review (§8) ran and its findings are recorded and
  resolved or explicitly deferred; the report shows real evidence (an actual offline-mode test, an
  actual CI run's wall-clock time), not "should work."
- **PARTIAL** — some parts shipped and are individually gate-clean, others are not; name exactly
  which.
- **BLOCKED** — cannot proceed because R3b/R4/R5 are not all `DONE`, or because the §2.5 deploy
  decision record does not yet exist and cannot be signed by whoever is executing this runbook.
- **IN_PROGRESS** — a long-running step (e.g. a Lighthouse audit run, a first Scaleway provision)
  is genuinely still executing when the session ends.
