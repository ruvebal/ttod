# Phase R7 — testing strategy (continuous, cross-cutting)

**Mode:** student lane, 1 owner, **continuous — not terminal** (read §0 before doing anything else)
**Owner:** one cohort student (assigned once the cohort-start gate opens — starts immediately, does
not wait for R3b/R4/R5 to finish)
**Task-package mapping:** "Testing" (cross-cutting)
**Entry:** cohort-start gate green (start); pairs with each lane owner as their feature lands
**Exit (closing gate, not the only place tests get written):** Playwright E2E across the assembled
app, the full contract-test pass, the CI wall-clock measurement — filed after R3b, R4, and R5 are
`DONE`

---

## 0. What this phase actually is — read this before anything else, it changes how you work

**R7 is continuous work, not a phase that starts only after R4/R5 finish.** Unlike every other
student lane in this cascade, R7's owner does **not** wait for other lanes to complete before
starting. From the moment the cohort-start gate opens, R7's owner should already be pairing with
each lane owner **as their feature lands**: writing the unit/component tests for R1's endpoints as
soon as the cohort-start gate opens (R1 is already `DONE` by definition of the gate being open —
start there immediately), the a11y assertions for R3b's docs routes as soon as they render, the
component tests for R4's graph island and R5's oracle terminal as soon as each has something
testable — not waiting for any of them to file their own `DONE` report first.

**This runbook's own `PHASE-R7-REPORT.md` is the suite-wide closing gate** — Playwright E2E across
the fully assembled app, the full contract-test pass, and the CI wall-clock measurement — filed
once R3b, R4, and R5 are all `DONE`. But that closing report is not "the place tests get written";
it is the point where the cumulative, continuously-written suite gets assembled and proven as a
whole. If you find yourself with nothing to test in the first days after the gate opens because
"nothing is DONE yet," that is a misunderstanding of this phase — R1 and R2 are already `DONE` by
the time the gate is open (that is what opens it), and they have real endpoints/tools to write
contract and unit tests against immediately.

## 2. Non-negotiable boundaries (restated in full)

### 2.1 Inherited from TTOD Phase Q — unconditional, no exceptions

- **`ttod.yml` has exactly one write path.** R7's tests must never run against the live,
  repository-root `ttod.yml` in a way that could mutate it — any test that exercises a write path
  (e.g. a hypothetical future test of `oracle/propose`'s actual proposal-writing behavior) must run
  against a disposable fixture/copy, exactly like Phase Q's own repository tests do, never the real
  file.
- **Provenance and creative-mode disclosure are testable claims, not vibes.** R7 writes the actual
  assertion that proves `origin: blackbox` content renders distinguishably and that a
  `mode: 'creative'` oracle response never appears as if it cites a real quote — these are gates in
  §7 of the master document that only a real test, not a runbook's prose, can actually close.
- **Rights gate.** A contract test confirms `/api/v1/wisdom/sample` and `/api/v1/graph` never emit
  a quote whose `rights` is unresolved/restricted or `status != active` — this is testable against
  the real corpus's actual shape, not a mock.

### 2.2 Testing strategy specifics (§0.1.4 of the master document, restated in full — this is R7's
actual mandate, not background)

- **Vitest + React Testing Library + MSW** for unit/component tests.
- **Playwright with the `chromium` project only** for E2E (matches `npx playwright install
  --with-deps chromium`) — Firefox/WebKit projects are **not required** unless a cross-browser bug
  surfaces; if one does, file it explicitly rather than silently expanding scope.
- **`@axe-core/playwright` assertions folded into the suite** rather than run as a separate audit —
  accessibility checks run on every PR inside the normal E2E suite, not as a pre-submission
  afterthought.
- **A contract-test suite that hits R1's real `/api/v1/*` endpoints and asserts shape** (against
  `schema/*.json`/`domain.ts`), **never values.** This is the exact pattern unit 5 §6 teaches,
  applied to a backend this cohort itself built — a nightly (not per-PR) suite, so a silent backend
  rename gets caught without slowing down every PR.
- **Trophy, not Pyramid**, for `services/frontend`: the bulk of tests are integration/component
  (R4's/R5's islands wired to real state), not isolated units; framework internals (Astro
  hydration, React rendering, Svelte reactivity) are never under test — testing that React renders
  is testing React, not this project.
- **CI budget: PR feedback stays under 5 minutes wall-clock** (R6 owns the CI orchestration that
  enforces this; R7 owns making sure the test suite's own runtime fits inside that budget) — cheap
  lint/typecheck gate first, unit/component tests next, Playwright E2E sharded across parallel jobs
  last.

### 2.3 The §3.1 calibration fixture — R7's own concrete deliverable, not a suggestion

R1's `oracle/stream` handler compares retrieval confidence against a threshold (**starting at
cosine ≈ 0.55–0.6, a starting point to tune, not an asserted-correct number**). "Calibrate
empirically" is not optional prose — **R7's runbook must include an actual calibration fixture**: a
small, named set of real or realistic queries paired with an expected `grounded`/`creative`
verdict, at `tests/fixtures/r_oracle_threshold_calibration.json` (mirroring Phase S's `s1_*` naming
discipline), **and a test asserting the chosen threshold produces the expected verdict on each** —
without that fixture and its assertion, "calibrate empirically" has no artifact anyone can point to
as done. Build this as soon as R1's `oracle/stream` is `DONE` — do not wait for R4/R5 to also be
done, this fixture only depends on R1 and R2.

### 2.4 Environment files and secrets discipline

**R7 does not introduce any new env var and needs no new secret.** Tests run against the local
walking-skeleton stack (or CI's own ephemeral instance of it), which needs zero real secrets. The
one place R7's tests touch anything secret-adjacent is the nightly contract-test suite hitting
R1's real endpoints — this runs against the same no-auth-needed local/CI stack, never against
Scaleway `stg` with real deploy credentials (that would be R6's CI job's concern, not R7's test
content). If a test task ever seems to need a real credential, stop and ask.

## 3. Domain contract R7 tests against

R7 does not own or edit `domain.ts` — it is the primary **consumer** of it as a contract-testing
target, asserting every interface's shape against live API responses:


   - Contract tests for `/health`, `/api/v1/schema/definitions`, `/api/v1/wisdom/sample`,
     `/api/v1/graph` — shape assertions against `schema/*.json`/`domain.ts`, never values.

     R1 and R2, build it now.
   - The `r_negative_oracle_propose_no_active.json` negative test (mirrors R1's own requirement) —
     confirm no code path in `oracle/propose` can set `status: active`.
   - First CI workflow skeleton (lint/typecheck + unit tests) — coordinate with R6 rather than
     building a competing workflow file.
   - A live contract assertion that R1 reaches R2 through FastMCP Streamable HTTP at `/mcp` and
     fails closed when R2 is unavailable. A Compose network entry alone is not evidence of this.
2. **As R3b's content lands:**
   - `@axe-core/playwright` a11y assertions for docs routes, folded into the normal E2E suite.
   - i18n route-resolution tests (`/en/`, `/es/` both resolve, default-locale fallback works).
3. **As R4's graph island lands:**
   - Component/integration tests for the graph island wired to real state (Trophy-shaped: does the
     graph render real nodes/edges and respond to interaction, not "does Svelte re-render on
     `$state` change").
   - A test confirming the URL-query sync channel (`?tag=<slug>`) actually works across islands.
4. **As R5's oracle terminal lands:**
   - Component/integration tests for the SSE reader and streaming state.
   - **The specific test this whole document treats as load-bearing:** a test that a
     `mode: 'creative'` response renders visibly distinguishable from `mode: 'grounded'`, and that
     `oracle/propose` is never called automatically, only on explicit user action.
5. **Closing gate, once R3b + R4 + R5 are all `DONE`:**
   - Full Playwright E2E suite across the assembled app.
   - Full contract-test pass, run nightly per §2.2.
   - CI wall-clock measurement — confirm the whole suite fits R6's 5-minute PR budget when sharded.
   - File `PHASE-R7-REPORT.md`.

## 6. Rollback and mutation law (restated in full)

- R7's tests never mutate `ttod.yml` — any test exercising a write-adjacent path runs against a
  disposable fixture/copy, never the live repository-root file.
- A failing/flaky test in R7's suite blocks CI, it does not silently get skipped or marked
  allow-failure without an explicit, reported reason — flakiness is a finding to fix or file, not
  to route around quietly (this mirrors unit 5's own framing on flakiness).

## 7. Touched-path budget

**Allowed:** `services/frontend/tests/**` (or wherever the syllabus's own convention places
Vitest/RTL/Playwright specs — confirm and use it consistently), `tests/fixtures/r_*` (backend-side
fixtures, mirroring TTOD's own `tests/fixtures/` convention), `docs/testing-strategy.md` (the
deliverable unit 5's own exercise names — R7 writes this doc, not a duplicate embedded elsewhere).

**Forbidden:** `ttod_core/*.py`, `schema/*.json`, the live repository-root `ttod.yml`,
`services/backend/**`/`services/mcp/**` **application code** (R7 writes tests *of* these, it does
not modify their implementation — a failing test gets reported to that lane's owner, not silently
"fixed" by loosening the test), R3b's/R4's/R5's own feature code, R6's CI workflow files (R7
contributes test *content* R6's workflows run — coordinate on the file, don't fork it).

## 8. Post-phase cold review (mandatory — not a formality, and ongoing, not just at closeout)

**Because R7 is continuous, its cold review is also continuous, not a single event at the end.**
Per the master document's §6.1, every phase report closes with a cold review — this applies to
R7's own closing `PHASE-R7-REPORT.md` the same as any other, using the studio's `/code-review`
skill (medium-to-high effort given the suite's cross-lane scope). But R7 also plays the reviewer
role for other lanes throughout: **when R7's owner writes a test for R4's or R5's feature and that
test reveals the feature doesn't actually meet its own runbook's gates, that is itself a form of
cold review — feed it back to that lane's report immediately, don't sit on it until R7's own
closing report.**

**Two propagation obligations if either kind of review finds something:**
1. If the finding only affects the test suite itself, fix it and move on.
2. **If the finding is structural** — a gate this whole document asserts is real turns out not to
   be provably true — gets escalated for the instructor to amend the master document itself.

## 9. Phase report status enum (restated — use exactly one)

- **DONE** — every gate in §5 passed; the closing cold review ran and its findings are recorded and
  resolved or explicitly deferred; the report shows real evidence (actual test output, actual CI
  timing), not "should work." R7's `DONE` additionally requires R3b, R4, and R5 to all be `DONE` —
  the closing E2E/contract pass cannot be meaningfully complete against an unfinished platform.
- **PARTIAL** — the continuous, per-lane testing work is ongoing/complete for some lanes but the
  closing suite-wide gate hasn't run yet (this is the *expected*, normal status for most of R7's
  life — it is not a red flag the way `PARTIAL` might be for a terminal phase); name exactly which
  lanes have their tests written and which don't yet.
- **BLOCKED** — cannot proceed on a specific piece because the lane it depends on is itself
  `BLOCKED` (e.g. can't write R5 component tests if R5 hasn't started).
- **IN_PROGRESS** — a long-running CI run or Lighthouse-adjacent measurement is genuinely still
  executing when the session ends.
