## 0. What this phase actually is, and the gate you must verify before starting

R5 builds the "oracle" chat terminal: a React 19 island that streams answers from R1's
`POST /api/v1/oracle/stream` (SSE), renders the grounded/creative distinction honestly, lets a user
explicitly crystallize a creative-mode answer into a proposal via `POST /api/v1/oracle/propose`,
and queues queries offline (IndexedDB) when the network is down.

**Do not start this phase until you have personally confirmed the cohort-start gate is open** —
read `docs/DEV_PLAN/PHASE-R1-REPORT.md`, `PHASE-R2-REPORT.md`, and `PHASE-R3a-REPORT.md` and
confirm each says `DONE`. Also read `PHASE-R3a-REPORT.md`'s "Lessons for the next phase" section in
full — the island-mount pattern you build against comes from there. If R4's report already exists,
skim its "Lessons for the next phase" section too — you share the URL-query sync channel (§3.1
below) with R4's graph island.

**Dependency note (§6 of the master document, restated):** R5 depends on the cohort-start gate —
specifically R1's and R2's endpoints and R3a's island-mount pattern — but explicitly **not on
R3b**. The graph/oracle lanes (R4, R5) run fully in parallel with the docs lane (R3b) from the
moment the gate opens.

**Two-role split (inherited from the original task-package breakdown):** one owner focuses on
streaming state — the SSE reader, session history, the offline IndexedDB queue and its
sync-on-reconnect logic; the other focuses on motion/hotkeys — Framer Motion entrance/exit, keyboard
shortcuts, the grounded/creative visual distinction, the `/propose` affordance. Both work inside
the same island directory; coordinate on the shared state shape.

## 2. Non-negotiable boundaries (restated in full)

### 2.1 Inherited from TTOD Phase Q — unconditional, no exceptions

- **`ttod.yml` has exactly one write path.** R5 never writes to `ttod.yml` directly or
  indirectly. It *may* call `POST /api/v1/oracle/propose` (R1's endpoint) — that writes a
  `status: proposed` proposal via `ttod_core.proposals`, never a canonical quote, and only ever in
  response to an **explicit, human-initiated action** (a `/propose` chat command or a clicked UI
  affordance) — **never automatically** as a side effect of receiving a creative-mode answer.
- **No silent provenance promotion.** A creative-mode answer must **never be presented as if it
  cites a real quote.** This is R5's single most important UI rule: `OracleResponseChunk.mode` is
  `'grounded' | 'creative'` — the terminal must render these two **distinguishably** (different
  visual treatment, an explicit label, whatever the design — but never the same treatment).
- **Rights gate is already applied upstream** — R5 does not need to re-filter cited quotes, R1's
  endpoint already only cites `status: active`, rights-resolved quotes in grounded mode.
- **Local-only AI** — irrelevant to R5 directly (it never calls Ollama itself, only R1's proxy
  endpoint), but R5 must never add a fallback path to a cloud LLM API "for reliability" — if
  `oracle/stream` is unreachable, the correct behavior is the offline queue (§4 below), not a
  silent cloud fallback.
- **Counts are never hardcoded** — irrelevant to most of R5's UI, but if R5 ever displays "N quotes
  in the corpus" anywhere (e.g. an empty-state message), that number must come from a live
  `backend` response.

### 2.2 Inherited from the stack draft, reconciled with studio infra

- **No heavy native dependencies** — the terminal must perform acceptably on an 8 GB RAM student
  laptop, including the IndexedDB offline queue.
- **Ollama is three-tier, not one switch** — irrelevant to R5 directly (that's R1's/R2's
  configuration surface), but R5 must not assume a specific model's latency/behavior in its UI
  logic (e.g. don't hardcode a streaming-speed assumption that only holds for the fast dev-tier
  model and breaks against the light containerized tier).

### 2.3 Cross-platform constraints

- Respect the root `.gitattributes` (`* text=auto eol=lf`) already established.
- IndexedDB behavior should be tested in more than one browser if practical (Safari's IndexedDB
  implementation has historically had quirks) — note in the report which browser(s) were actually
  tested, don't assume Chrome-only testing generalizes.

### 2.4 Environment files and secrets discipline

**R5 does not introduce any new env var and needs no new secret.** It is a pure client-side island
calling R1's already-configured proxy endpoint — R5 never talks to Ollama directly, never needs an
Ollama URL or model tag of its own. If an oracle-terminal task ever seems to need something that
looks like a real credential, that is a signal something has gone off-script — stop and ask.

## 3. Domain contract slice R5 consumes and produces

```typescript
// Request payload for POST /api/v1/oracle/stream.
export interface OracleQueryPayload {
	query: string;
	contextTag?: string; // synced from the graph island's selected node (§3.1 below)
	sessionHistory: string[];
}

// SSE response envelope for /api/v1/oracle/stream. "mode" is the grounded/creative marker — the
// terminal MUST render these two distinguishably; a creative answer is never shown as if it cites
// a real quote.
export interface OracleResponseChunk {
	mode: 'grounded' | 'creative';
	citedQuoteIds?: string[]; // present only when mode === 'grounded'
	text: string; // streamed token/segment
}

// Body for POST /api/v1/oracle/propose — human-initiated only, never automatic. Writes a proposal
// (origin: blackbox), never a canonical quote — same governance as Phase S's translate-draft.
export interface OracleProposeRequest {
	query: string;
	creativeAnswer: string;
	suggestedSection?: string; // pre-filled by R1 from below-threshold nearest neighbors
	suggestedTags?: string[]; // "the tags around" — a starting point, not a final answer
}

// src/lib/db.ts IndexedDB record for the offline chat/error queue.
export interface OfflineLogEntry {
	id: string;
	timestamp: string; // ISO-8601
	kind: 'oracle-query' | 'error-report';
	payload: OracleQueryPayload | { errorLog: string };
	synced: boolean;
}
```

**Do not hand-edit `domain.ts`.** It is R1's contract; if R5 needs a shape R1 does not yet expose,
request it as an R1 addition.

### 3.1 Routing/navigation sync (hard requirement, shared with R4)

The React terminal island reads the URL query (`?tag=<slug>`, written by R4's graph island on node
click) to seed `OracleQueryPayload.contextTag` for the next oracle query. **This is the only state
channel between islands — no shared client store.** R5 reads this value, it does not write it (only
R4 writes it, on graph-node click) — if R5's own UI needs to change the active tag context, do so
by updating the same URL query parameter, not a separate mechanism.

### 3.2 Known, currently-live blocker inherited from Phase S — R5's UI must not imply this works

`ttod_core/repository.py` currently rejects every `origin: blackbox` proposal at accept time
(`"blackbox origin requires validation.reviewer_id before accept"`), and no existing CLI path can
satisfy that check (confirmed live in the code as of R0's generation pass). This means: after a
student clicks "propose this" and `oracle/propose` succeeds, **the proposal is genuinely staged but
currently cannot be accepted by a human through any existing tool.** R5's UI must not claim or imply
"your suggestion has been submitted for review and will be processed" in a way that promises a
working review pipeline — a simple, honest "your suggestion was saved as a draft proposal" is
accurate; do not build a fake "pending review" status tracker that implies more automation than
exists. This is a pre-existing Phase S–level gap, not something R5 caused or must fix.

## 4. Scope — what R5 builds

1. **SSE reader + streaming state.** Consumes `POST /api/v1/oracle/stream`'s server-sent events,
   accumulates `OracleResponseChunk.text` into a rendered, incrementally-updating answer, tracks
   `mode` for the whole response (it should not change mid-stream, but defend against it anyway —
   render whatever the server says per-chunk, don't assume single-mode-per-response as an
   invariant the backend guarantees).
2. **Grounded/creative visual distinction.** A clear, honest UI treatment distinguishing a
   `mode: 'grounded'` answer (with `citedQuoteIds`, rendered as real citations, e.g. linking to
   R3b's `/[locale]/wisdom/[slug]` pages) from a `mode: 'creative'` answer (visibly marked as not
   sourced from the corpus).
3. **`/propose` affordance.** A chat command or UI button, visible only on a creative-mode
   response, that calls `POST /api/v1/oracle/propose` with the prior exchange — see §3.2's honesty
   requirement about what this actually does.
4. **Framer Motion.** Terminal entrance/exit animation.
5. **Hotkeys.** Keyboard shortcuts for common actions (open terminal, submit query, etc. — design
   choice, but must not conflict with browser/OS-reserved shortcuts).
6. **IndexedDB offline queue (`src/lib/db.ts`).** When `oracle/stream` is unreachable, queue the
   query as an `OfflineLogEntry` (`kind: 'oracle-query'`) rather than failing silently; flush queued
   entries and attempt them again on reconnect. Same mechanism handles `kind: 'error-report'`
   entries for client-side error logging.
7. **Language reflection, not translation.** The terminal displays whatever language R1's backend
   already answered in (§5.1 of R1's runbook: language-matching, not translation) — R5 implements
   **no client-side translation logic** of its own; it is a pure display of what the backend
   returned.

## 6. Rollback and mutation law (restated in full)

- The web layer is read-only against `ttod.yml` under all circumstances; R5's one write-adjacent
  action (`oracle/propose`) only ever stages a proposal via R1's endpoint, never touches `ttod.yml`
  itself, and requires an explicit human action to trigger.
- A staged proposal is inert until a human runs `proposal review`/`proposal accept` — R5 introduces
  no new acceptance path and must not imply one exists (§3.2).
- A rendering/streaming bug in R5 never touches `ttod.yml`, `schema/`, `exports/`, or any other
  service's code.
