## 0. What this phase actually is, and the gate you must verify before starting

R4 builds an interactive Svelte 5 island that visualizes the TTOD corpus as a graph — nodes are
quotes, edges are the relational fields already encoded in `ttod.yml` (§3 below explains exactly
how). This is a **client-side layout and interaction problem**, not a data-modeling problem: the
backend (R1) ships raw `{nodes, edges}` topology only; R4 owns everything about how that topology
gets laid out, animated, and made navigable.

**Do not start this phase until you have personally confirmed the cohort-start gate is open** —
read `docs/DEV_PLAN/PHASE-R1-REPORT.md`, `PHASE-R2-REPORT.md`, and `PHASE-R3a-REPORT.md` and
confirm each says `DONE`. Also read `PHASE-R3a-REPORT.md`'s "Lessons for the next phase" section in
full — the island-mount pattern you build against comes from there.

**Dependency note (§6 of the master document, restated, and important — read this carefully):** R4
depends on the cohort-start gate — specifically **R1's `/api/v1/graph` endpoint and R3a's
island-mount pattern** — but explicitly **not on R3b**. You do not wait for the content engine to
be finished; the graph/oracle lanes (R4, R5) run fully in parallel with the docs lane (R3b) from
the moment the gate opens. If you find yourself blocked waiting on an R3b deliverable, that is a
misunderstanding of the dependency graph, not a real blocker — check with the instructor.

**Two-role split (inherited from the original task-package breakdown, not invented here):** one
owner focuses on data/canvas — fetching `/api/v1/graph`, running the layout algorithm, rendering
nodes/edges to SVG/canvas; the other focuses on animation — GSAP micro-interactions, node
physics/hover, transition animation when the layout recomputes (e.g. after a tag filter). Both work
inside the same island directory; coordinate on the shared `$state` shape rather than each building
a parallel one.

## 2. Non-negotiable boundaries (restated in full)

### 2.1 Inherited from TTOD Phase Q — unconditional, no exceptions

- **`ttod.yml` has exactly one write path.** R4 is a **pure read-only consumer** of
  `GET /api/v1/graph` — it never writes anything, never calls a proposal/accept path, never
  attempts a second, uncontrolled way to touch quote data.
- **Provenance stays visible.** If R4's node rendering encodes `origin` visually (e.g. a color/icon
  per origin type — a reasonable, encouraged design choice), it must render `origin: blackbox`
  distinguishably, not blend it in with `human`/`studio` nodes as if equally authoritative.
- **Rights gate is already applied upstream.** `GET /api/v1/graph` (R1) already returns only
  `status: active`, rights-resolved nodes — R4 does not need to re-filter, and must not bypass this
  endpoint to fetch graph data any other way.
- **Counts are never hardcoded.** Any node/edge count shown in the graph UI (a legend, a "N nodes
  in this section" label) is derived from the live `/api/v1/graph` response, never a fixed number.

### 2.2 Inherited from the stack draft, reconciled with studio infra

- **No heavy external DB** — irrelevant to R4 directly (it's a frontend island), but relevant to
  why the graph is even shaped this way: it is a computed projection of `ttod.yml`, not a
  materialized graph table, so R4 must treat every `/api/v1/graph` response as the current
  ground truth, never cache it stale across a session in a way that could show an outdated graph
  after a quote is deprecated.
- **No heavy native dependencies** — the graph rendering must perform acceptably on an 8 GB RAM
  student laptop; if the corpus grows, prefer an efficient layout algorithm over brute-force
  force-direction on every frame.

### 2.3 Cross-platform constraints

- Respect the root `.gitattributes` (`* text=auto eol=lf`) already established.
- Build/test locally with whatever orchestrator R3a's onboarding doc specifies.

### 2.4 Environment files and secrets discipline

**R4 does not introduce any new env var and needs no new secret.** It is a pure client-side island
consuming an already-authenticated (auth-free, in fact — this stack has no auth layer) backend API.
If a graph-rendering task ever seems to need something that looks like a real credential, that is a
signal something has gone off-script — stop and ask.

## 3. Domain contract slice R4 consumes, and how the graph is derived from `ttod.yml`

```typescript
// Matches ttod_core/exporter.py Exporter._graph_nodes() exactly. No invented "label"/"group".
export interface GraphNode {
	id: string;
	section: string;
	origin: 'human' | 'studio' | 'blackbox' | 'mixed' | 'legacy-unknown';
	status: 'active' | 'deprecated' | 'erased';
	text: string;
	lang: string; // ISO 639-1
}

// Matches Exporter._graph_edges(): "rel" is a real relation type, not a fabricated numeric weight.
export interface GraphLink {
	source: string;
	target: string;
	rel: 'related' | 'immediate_parent' | 'root_source' | 'deprecated_by' | 'superseded_by' | 'translation_of';
}
```

**There is no separate graph store to design.** The graph is a computed projection of the same flat
quote list, structurally identical to building a graph from a relational table's foreign keys,
applied to YAML records:

1. **Nodes = quotes, trimmed.** Every record under `ttod.yml`'s `quotes:` list becomes exactly one
   `GraphNode`. No layout information (no x/y, no size) lives in the data — **that is R4's job**.
2. **Edges = relational fields, flattened**, one `{source, target, rel}` triple per relation:

   | Field on the quote | Emitted edge `rel` | Meaning |
   | --- | --- | --- |
   | `related: [id, ...]` | `related` | generic cross-reference |
   | `relation_edges: [{target, relation_type}]` | `<relation_type>` | typed relationship |
   | `relation_edges: [{target, relation_type: "translation_of"}]` | `translation_of` | this record is a translation of `target` (one-way; the original carries no reverse edge) |
   | `immediate_parent_refs: [id]` | `immediate_parent` | direct derivation ancestor |
   | `root_source_refs: [id]` | `root_source` | deep ancestry, may skip intermediate parents |
   | `deprecated_by` | `deprecated_by` | lifecycle: replaced by |
   | `superseded_by` | `superseded_by` | lifecycle: superseded by |

   Concrete example: if `arch-010` has `related: [arch-013]` and `arch-020` has
   `immediate_parent_refs: [arch-010]`, the graph gains two edges —
   `{source: arch-010, target: arch-013, rel: related}` and
   `{source: arch-020, target: arch-010, rel: immediate_parent}`.

3. **`GET /api/v1/graph` (R1) calls the same `export_graph`/`_graph_nodes`/`_graph_edges` code
   `cli.py graph` already calls** — never a materialized graph table that could drift from the
   YAML. Two clean calls for the same snapshot are byte-identical.
4. **Layout is R4's job, not the data's.** R4 receives `{nodes, edges}` topology only and runs its
   own layout (force-directed or radial-by-`section`) client-side; GSAP animates transitions when
   the layout recomputes (e.g. after a tag filter). **The backend never ships coordinates** — do
   not request or expect an x/y field from R1; if you find yourself wanting one, the layout logic
   belongs in R4, not as a backend feature request.

### 3.1 Routing/navigation sync (hard requirement, shared with R5)

Clicking a graph node updates the URL query (`?tag=<slug>`), which the static docs routes (R3b)
read to filter content, and which the React terminal island (R5) reads to seed
`OracleQueryPayload.contextTag` for the next oracle query. **This is the only state channel between
islands — no shared client store.** R4 must write to the URL query string on node click/selection,
not to a global JS variable, a custom event bus, or localStorage.

## 4. Scope — what R4 builds

1. **Data fetch + `$state`.** Svelte 5 runes-based state holding the fetched `{nodes, edges}` and
   any derived UI state (selected node, active tag filter). Because the frozen `GraphNode` wire
   projection intentionally has no `tags`, also fetch `/api/v1/wisdom/sample` and join
   `WisdomEntry.tags` by quote ID; do not mislabel `section` as a tag or change `domain.ts`.
2. **Layout algorithm.** Force-directed or radial-by-`section`, computed client-side, re-run when
   the filtered node/edge set changes.
3. **Rendering.** SVG or canvas rendering of nodes/edges — pick one and be consistent; encode
   `origin`/`status` visually in a way that keeps `blackbox`-origin and `deprecated`-status content
   visibly distinguishable (§2.1).
4. **GSAP micro-animations.** Node physics/hover, and transition animation when the layout
   recomputes after a filter change.
5. **URL query sync.** Node click → `?tag=<slug>` in the URL (§3.1) — the one inter-island
   communication channel.
6. **Tag/section navigation** — filtering the visible graph by section or tag, driven by the same
   URL query state R3b's docs routes also read.

## 6. Rollback and mutation law (restated in full)

- The web layer is read-only against `ttod.yml` under all circumstances — R4 introduces no write
  path whatsoever.
- A rendering/layout bug in R4 never touches `ttod.yml`, `schema/`, `exports/`, or any other
  service's code — its blast radius is its own island directory and, via the URL query string, the
  visible filter state of R3b's docs routes (a read-effect, not a data mutation).

R6 reads it before starting (needs R3b, R4, R5 all `DONE`).
