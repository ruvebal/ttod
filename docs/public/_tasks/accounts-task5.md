# Assignment — Team 5, Task 5: A bearer-token-authenticated public API endpoint (GET a random quote)

**Seam:** accounts · **Team:** 5 · **Task:** 5 of ~10
**Area(s):** Accounts · **Verb served:** contribute

## 1. Curriculum map

This task exercises the core concepts of **Unit 3 — Framework-mode authentication and session management** from the web-atelier-udit FE II curriculum, specifically the distinction between server-side session guards and API bearer token authentication. The module brief explicitly maps this to FE I's `tokenStorage.js` + `Authorization: Bearer` pattern, which is the foundational concept being extended here.

## 2. Worked example, from the real TTOD app

The backend already implements the bearer token issuance mechanism that this task consumes. In `services/backend/app/auth.py`, `AuthService.issue_pat(user)` signs `{sub, role, typ: "pat"}` with `URLSafeTimedSerializer` (a timed, signed token — not a JWT) using a secret distinct from the session cookie's own signer. The `create_auth_router()` route handler wraps this in a `TokenResponse` with `token_type: "Bearer"`. The existing test `test_auth_login_me_token_logout_are_separate_credentials` in `services/backend/tests/test_backend.py` confirms that `POST /api/v1/auth/token` returns a token that is genuinely separate from the session credential.

The current `services/backend/app/main.py` exposes `GET /api/v1/wisdom/sample` as an unauthenticated endpoint. This task extends that pattern by adding `GET /api/v1/wisdom/random` with bearer token authentication, following the same architectural approach but with the security gate that the module brief requires.

## 3. What "done" looks like

**Visible result:** An external client (not a browser) can call `GET /api/v1/wisdom/random` with `Authorization: Bearer <token>` and receive a quote back. The token comes from `POST /api/v1/auth/token` — a genuinely separate credential from the session cookie, never the same signed value reused in both places.

**What it includes:**
- A new endpoint `GET /api/v1/wisdom/random` in `services/backend/app/main.py`
- Bearer token authentication middleware that validates the `Authorization: Bearer <token>` header
- Rejection of requests with no token, an invalid token, and a valid session cookie presented as if it were a bearer token
- The endpoint returns a random quote from the TTOD corpus

**What has to be done:**
1. Add a new route handler for `GET /api/v1/wisdom/random` in `services/backend/app/main.py`
2. Implement bearer token validation that extracts the token from the `Authorization` header, validates it with `AuthService.read_pat(token)` (the same PAT signer `POST /api/v1/auth/token` uses), and rejects invalid or missing tokens
3. Ensure the endpoint explicitly rejects session cookies — a valid session cookie sent in the `Cookie` header must not authenticate this endpoint
4. Return a random quote from the corpus in a consistent JSON format
5. Add tests that verify: (a) valid bearer token succeeds, (b) missing token fails, (c) invalid token fails, (d) session cookie alone fails

## 4. Success criteria (functional)

From the parent module `ASSIGNMENT.md`'s Acceptance criteria:

- **Bearer surface:** A logged-in session can `POST /api/v1/auth/token`, receive a PAT shown once, and a non-browser client can call a documented API with `Authorization: Bearer`. That token must not be the session cookie value.

This task specifically closes the "non-browser client can call a documented API with `Authorization: Bearer`" requirement by implementing the `GET /api/v1/wisdom/random` endpoint with proper bearer token authentication.

## 5. Quality criteria (the part that's new)

**Code organization:** The bearer token validation logic should be extracted into a reusable dependency or middleware function in `services/backend/app/auth.py` or a new `services/backend/app/api_auth.py` module, not duplicated inline in the route handler. This follows the module brief's constraint to "reuse the seam" rather than invent a second auth stack.

**AI-use/process documentation discipline:** Document in the PR description that this endpoint is bearer-token-only and explicitly state that session cookies are rejected. Include a note that the token is generated by `POST /api/v1/auth/token` and is a separate credential from the session.

**Test shape per the Testing Trophy (not Pyramid) doctrine:** The tests should be focused and specific:
- One test for successful authentication with a valid bearer token
- One test for missing token (401 response)
- One test for invalid token (401 response)
- One test for session cookie presented as bearer (401 response)
- One test verifying the response contains a valid quote structure

Each test should be independent and test one specific behavior. Avoid testing implementation details like the exact PAT payload structure; test the observable behavior (status code, response shape).

**Accessibility:** This is a backend API endpoint, so the standard accessibility Definition of Done (keyboard-operable, one accessible name or label, no meaning carried by color alone, respects reduced-motion preferences) does not apply directly. However, the JSON response structure should be consistent and predictable for client-side accessibility implementations.

**Defensible oral-defense answer:** "This endpoint implements bearer token authentication as a separate credential from the session cookie, following the module brief's requirement that 'a leaked PAT must not be a live browser session, and a stolen cookie must not be a PAT.' The validation logic is extracted into a reusable dependency to avoid duplicating auth logic, and the tests verify that session cookies are explicitly rejected, ensuring the two credential types remain separate." Test shape per [Unit 5 — Testing strategy](https://ruvebal.github.io/web-atelier-udit/lessons/en/feii/unit-5-testing-strategy/).

## Closing

> "When the same thing has two names, confusion reigns. When one thing serves two masters, both are betrayed."
> — TTOD `arch-015`, *architecture*

A session cookie and a bearer token both mean "this request is authenticated" — close enough that collapsing them into one value would go unnoticed for a while, and be a real vulnerability the whole while. Two masters, two names, two secrets: this task is keeping that distinction real at the one endpoint where it would be easiest to quietly blur.
